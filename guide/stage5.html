Stage 5 • Pro Features

Professional features nobody explains

This stage is the difference between “a site” and “a product”: media pipelines, email, reliability, logging, rate limits, analytics, and UX polish.

1) Media hosting with Cloudinary (the pro pipeline)

Uploading images directly into your repo is fine for tiny projects, but products need a pipeline: upload → transform → deliver fast. Cloudinary gives you optimized delivery and transformations.

Why Cloudinary matters

  • Automatic format selection (WebP/AVIF where supported)
  • Resize/crop on the fly (thumbnails, banners)
  • CDN delivery

Example URL pattern (concept)

https://res.cloudinary.com/<cloud>/image/upload/
  f_auto,q_auto,w_1200,c_fill,g_auto/
  your-folder/hero.jpg
Pro trick: Always serve responsive images. Don’t ship a 4000px hero to a phone.

2) Email: templates + domain email (name@yourdomain.com)

Email is a core product feature: onboarding, password resets, receipts, notifications. And domain email makes you look instantly more legit.

Set up domain email (high level)

  1. Choose email provider (workspace-style or forwarding)
  2. Add MX records in DNS (routes email)
  3. Add SPF TXT record (who can send)
  4. Add DKIM TXT record (signature)
  5. Add DMARC TXT record (policy + reporting)
Deliverability pro tip: Without SPF/DKIM/DMARC, your emails are more likely to be spam.

Transactional email sending (concept)

Typical backend flow:

POST /api/contact
  - validate input
  - store in DB
  - send transactional email
  - return ok

Don’t leak secrets

  • API keys only in server env vars
  • No keys in client JS
  • Log safely (no passwords, no tokens)

3) Logging, monitoring, and “debugging in production”

When users report “it’s broken,” you need evidence. You don’t guess—you observe.

What to log

  • Request ID, route, status code, latency
  • User ID (if authenticated), but not sensitive PII
  • Errors with stack traces (server-side)

Pro pattern: request IDs

const requestId = crypto.randomUUID();
console.log({ requestId, route: req.path });
Pro trick: Put the request ID in the response so the user can screenshot it and you can find it in logs.

4) Rate limiting (protect your API)

If you have a contact form or login endpoint, bots will spam it. Rate limiting reduces abuse.

Simple rule example

/api/contact:
- max 5 requests per minute per IP
- blocklist suspicious patterns
Rate limiting is easiest at the edge (CDN/Workers) because it’s close to the user and faster to enforce.

Legal basics (don’t skip)

  • Privacy policy (if you collect data)
  • Cookie notice if required in your region
  • Terms of service if you offer accounts/paid features

Not legal advice—use a lawyer for serious products.

5) Hidden pro developer tricks (the spicy ones)

“Make it feel expensive” checklist

  • Reduce visual noise: fewer borders, more spacing
  • Use one accent color, not five
  • Motion: 120–220ms transitions, ease-out
  • Consistent radii and shadows
  • Text: line-height 1.5–1.7 for paragraphs

Performance hacks

  • Ship fewer fonts/weights
  • Use image compression + responsive sizes
  • Defer non-critical scripts
  • Only animate transform/opacity

Reliability habits

  • Feature flags for risky changes
  • Rollback plan before deploy
  • Backups for DB
  • Staging environment for big releases

Product thinking

  • Measure activation (first success action)
  • Make onboarding 3 steps max
  • Log drop-off points
  • Write clear empty states

Stage 5 assignment

  1. Pick a media strategy (local assets vs Cloudinary)
  2. Draft a transactional email template (welcome or password reset)
  3. Add basic logging to your API (request IDs)
  4. Create a rate limit plan for your public endpoints

Stage 5 launch checklist

  • Media pipeline decided
  • Email authentication terms understood (SPF/DKIM/DMARC)
  • Logging plan exists
  • Rate limiting plan exists
