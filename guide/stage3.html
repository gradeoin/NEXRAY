Stage 3 • Backend

Backend from scratch: APIs, DBs, auth

Frontend is what people see. Backend is what makes it real: data, logins, permissions, payments, emails. You’ll learn the architecture and copy working code patterns.

← Prev: Stage 2 Next: Stage 4 →

1) Backend mental model

API

A set of endpoints your frontend can call. Typically JSON over HTTP: GET /posts, POST /login, POST /checkout.

Database

Stores data. You choose SQL (structured, relational) or NoSQL (document/scale‑friendly). Both are valid.

Pro rule: Always validate data on the server. Frontend validation is UX. Server validation is security.

2) Build a tiny Node.js API (learning fundamentals)

This is what “backend from scratch” means. You can host this API on a server or convert it to serverless later.

Create a folder (example)

api/
  package.json
  server.js

package.json

{
  "name": "nexray-api",
  "type": "module",
  "private": true,
  "scripts": {
    "dev": "node server.js"
  },
  "dependencies": {
    "cors": "^2.8.5",
    "express": "^4.19.2"
  }
}

server.js (Express)

import express from "express";
import cors from "cors";

const app = express();
app.use(cors());
app.use(express.json());

app.get("/health", (req, res) => {
  res.json({ ok: true, time: new Date().toISOString() });
});

app.get("/api/posts", (req, res) => {
  res.json([
    { id: "1", title: "Ship your first site", stage: 1 },
    { id: "2", title: "Make UI feel expensive", stage: 2 }
  ]);
});

app.post("/api/contact", (req, res) => {
  const { name, email, topic, message } = req.body || {};
  if (!name || !email || !topic || !message) {
    return res.status(400).json({ ok: false, error: "Missing fields" });
  }

  // In real life: store in DB + send email
  res.json({ ok: true, received: { name, email, topic } });
});

app.listen(8787, () => console.log("API on http://localhost:8787"));

Run it

cd api
npm i
npm run dev

# then visit:
# http://localhost:8787/health

Why serverless exists

Servers are always-on processes. Serverless runs code on demand. In 2026, many production apps use serverless for APIs.

  • Server: simple mental model, more ops
  • Serverless: less ops, more platform rules
You can learn with Express, then deploy the same logic using a Workers/Functions platform.

3) Databases: SQL vs NoSQL (choose based on your product)

SQL (Postgres)

Great when you have relationships: users → posts → comments, orders → line_items, etc. Strong constraints keep data clean.

Example schema

CREATE TABLE users (
  id UUID PRIMARY KEY,
  email TEXT UNIQUE NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE TABLE posts (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES users(id),
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

NoSQL (Firestore-like)

Great when you want rapid iteration, flexible docs, and simple scaling. You typically denormalize (duplicate) some data for fast reads.

Example document shape

// users/{userId}
{
  "email": "you@domain.com",
  "displayName": "You",
  "createdAt": 1710000000
}

// posts/{postId}
{
  "userId": "abc",
  "userDisplayName": "You",   // denormalized
  "title": "Ship it",
  "body": "Details...",
  "createdAt": 1710000000
}
Pro rule: Your database choice is less important than your data model and your permission model.

4) Authentication (Google + email/password + OAuth)

Auth is not just “login.” It’s identity + sessions + permissions. In 2026 the safest approach is: use a proven auth provider (Firebase Auth, Auth0, Clerk, etc.) unless you have a very good reason.

Email/password flow (concept)

  1. User submits email/password
  2. Server verifies
  3. Server issues a session (cookie) or token
  4. Frontend stores session safely and calls authenticated endpoints

Google sign-in (OAuth) concept

  1. User clicks “Continue with Google”
  2. Redirect to Google
  3. Google returns an authorization code
  4. Your backend/provider exchanges code for tokens
  5. You receive user identity and start a session
Pro warning: Don’t roll your own password hashing + session system for your first product. Learn it academically, but ship with a provider.

Token storage (important)

  • HTTP-only cookies are safer against XSS token theft.
  • localStorage is convenient but riskier (XSS).
  • Use CSRF protection when using cookies.
For MVPs with trusted auth providers, follow their recommended pattern.

5) A real “permissions” model (nobody tells beginners)

Most apps fail because permissions are vague. Decide early:

  • Who can read what?
  • Who can write what?
  • Who is the owner of a record?
  • What is public vs private?

Example policy (simple)

Posts:
- Anyone can read published posts
- Only the owner can edit/delete their posts
- Admin can moderate

Users:
- Users can read their own profile
- Users can update their own displayName
- Email is private
Pro trick: Write these rules in plain English first, then translate into database rules / middleware.

Stage 3 assignment

  1. Create a /api/posts endpoint (mock data is fine)
  2. Fetch it from the frontend and render on a new page (posts.html)
  3. Choose a DB direction (SQL or NoSQL) and write your data model in a README
  4. Pick an auth provider for future stages

Stage 3 launch checklist

  • API has a health endpoint
  • Input validation is enforced server-side
  • Permission rules are written in plain English
  • You understand tokens vs sessions
