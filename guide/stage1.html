What is a website (really) + your first deploy

We’re starting from absolute zero, but we’re not staying there. You’ll understand how websites work, write real HTML, and deploy for free—then learn domains + DNS like a pro.

0) The mental model (the only one you need)

Website = files served over HTTP

A basic website is just files: HTML, CSS, JS, images. A web server sends those files to the browser over HTTP/HTTPS.

Browser = renderer + runtime

The browser downloads HTML → builds a DOM tree → downloads CSS/JS → renders pixels. JS runs in a sandbox (security!), calling APIs like fetch().

Reality check: You don’t need a framework to make a great website. You need good fundamentals and good taste. Frameworks help you scale complexity later.

1) Your first page (HTML essentials)

HTML is structure + meaning. Not “just tags.” Use semantic elements so humans, screen readers, and search engines understand your page.

Minimal HTML template (copy/paste)

<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>My First Site</title>
  </head>
  <body>
    <header>...</header>
    <main>
      <h1>Hello world</h1>
      <p>I exist on the internet.</p>
    </main>
    <footer>...</footer>
  </body>
</html>

Semantic tags you should actually use

  • <header>, <nav>, <main>, <section>, <article>, <footer>
  • <button> for actions, <a> for navigation
  • One <h1> per page (usually)

2 rules that save you years

  • Don’t fight the browser. Work with standards.
  • Don’t over‑engineer. Ship simple, iterate.
Pro habit: Always set meta viewport and use semantic HTML. That’s accessibility + mobile readiness from day 1.

2) Free hosting (no domain required)

In 2026, you can publish a site for free in minutes. You’ll get a URL like yourproject.hosting.app (a subdomain). That’s still a real website.

Option A: GitHub Pages

Best for static sites, docs, portfolios. Simple + free.

  1. Create a repo
  2. Push your files
  3. Enable Pages in repo settings

Great for learning + public projects.

Option B: Netlify / Vercel

Instant deploy from GitHub + preview links.

  1. Connect GitHub repo
  2. Choose build settings (or “no build”)
  3. Deploy → get a URL

Best dev UX for small teams.

Option C: Cloudflare Pages

Fast global CDN + integrates with Workers.

  1. Connect repo
  2. Deploy Pages
  3. Optional: attach Workers API later

Great when you want edge features.

You do NOT need to buy a domain to learn or to ship an MVP. Buy a domain when you’re ready to brand it (Stage 7 shows how to launch).

3) Domains + DNS (explain it like a pro)

A domain is your human-friendly name (like yourbrand.com). DNS is the phonebook that maps that name to servers. When someone types your domain, DNS answers: “Here’s where that site lives.”

Key terms

  • Registrar: where you buy a domain (Cloudflare Registrar, Namecheap, etc.)
  • DNS provider: where your DNS records are managed (often Cloudflare)
  • Nameservers: tell the domain which DNS provider to trust
  • Records: the actual mapping rules (A, AAAA, CNAME, TXT…)

Records you’ll actually use

Record What it does Example
A Maps a name to an IPv4 address example.com → 93.184.216.34
AAAA Maps a name to an IPv6 address example.com → 2606:…
CNAME Alias one name to another name www → yoursite.pages.dev
TXT Verification + email security (SPF/DKIM/DMARC) v=spf1 include:…
MX Routes email for your domain mail.yourdomain.com
DNS propagation: changes aren’t always instant. It can take minutes to hours depending on TTL and caching. (Cloudflare is usually fast, but caches exist.)

How to buy a domain (step‑by‑step)

  1. Pick a domain you can say out loud (brandable + spellable)
  2. Buy at a registrar (often Cloudflare Registrar for cost)
  3. Set your DNS provider (Cloudflare recommended for CDN + security)
  4. Create records: @ (root) and www
  5. Enable HTTPS on your host

Root vs www

  • @ = root domain (yourdomain.com)
  • www = subdomain (www.yourdomain.com)
Common setup: Make both work. Either redirect one to the other or serve the same site on both.

4) Your first “real” project structure

Multi‑page sites are a cheat code for learning: you naturally learn navigation, shared layout patterns, and content structure. 

project/
  index.html
  about.html
  contact.html
  guide/
    stage1.html
    stage2.html
  css/
    style.css
  js/
    app.js

Linking between pages

<!-- from index.html to a stage page -->
<a href="guide/stage1.html">Start Stage 1</a>

<!-- from stage page back to home -->
<a href="../index.html">Home</a>
Rule: Relative links depend on the file location. Stage pages live in guide/, so they use ../ to reach root files.

5) Tiny JavaScript (what it’s for)

JavaScript adds behavior: menu toggles, animations, form handling, fetching data from APIs. In this project, JS handles the nav menu, search focus, and contact form drafts.

Example: select an element and change text

const title = document.querySelector('h1');
title.textContent = 'I just updated the page!';

Example: button click

const btn = document.querySelector('#myButton');
btn.addEventListener('click', () => {
  alert('Clicked!');
});

Launch checklist (Stage 1)

  • Site opens on mobile (no horizontal scroll)
  • Nav works with keyboard + screen readers
  • Deployed somewhere free
  • You can explain domains and DNS in 30 seconds
